# Segmently Modules CLI contract (for pipelines)

> Start here: [README](../README.md) — install, a 5-minute walkthrough, brownfield adoption.
> Every config section and key, packs and the lint codes: [configuration.md](configuration.md).

Every verb accepts `--root DIR` (default: nearest directory with `.segmently-modules/` or
`modules/registry.json`, else the nearest `.git`; `init`: the git top-level of the current
directory, else the current directory), `--config-dir DIR` (default `<root>/.segmently-modules`) and
`--json`.

- **stdout with `--json`:** exactly one JSON document `{"schema": "segmently-modules.<verb>/1", "data": …}`.
- **Exit codes:** `0` ok · `1` findings (lint at/above `--fail-on`, coverage below
  `--fail-under`, a failed `ci` step, `eval routing` below its hit-rate threshold, rejected proposals, a failed required hook, a stale index with `--check`, a
  pointer stub, `init done` naming problems of a staging output, `init run` / `init resume --executor` with a failed module or a write outside the staging dir, `init eval-tasks` whose tasks file is missing or wrong, `init verify` that does not pass, `init finish --open-pr` whose push or `gh` failed) · `2` usage, config or registry error (a missing registry says to run
  `segmently-modules init`) — stdout is empty, stderr carries `segmently-modules: error: …`. The one extra code is `130`:
  interrupted by Ctrl-C (SIGINT, e.g. during a lock wait or at a `create` prompt), stderr
  `segmently-modules: interrupted`.
- **Never a traceback:** an unexpected failure is exit `2` with `segmently-modules: internal error: …`;
  set `SEGMENTLY_MODULES_DEBUG=1` to see the traceback.
- **A closed stdout reader** (`segmently-modules catalog --json | head -1`, a pager that quits): the
  rest of the output is dropped silently — no extra stderr line (a refusal keeps its
  `segmently-modules: error: …` line, a deferred note still prints) and no `Exception ignored` at
  exit; the verb still runs to its end (a writer still writes) and the exit code is the verb's own
  exit code (`0` / `1` / `2`; Ctrl-C stays `130`); `--help` and `--version` into a closed reader
  exit `0` silently. A closed stderr reader is dropped the same way. With stderr open, any other
  stdout write error (a full disk, a file size limit) is exit `2` with one stderr line
  `segmently-modules: error: cannot write stdout: <reason>`.
- **stderr closed at start** (`segmently-modules … 2>&-`): no line meant for stderr reaches stdout —
  a refusal, a usage error, an internal error and an interrupt leave stdout empty and keep their
  exit code. When fd 2 is closed at start the run puts the null device on fd 2 itself (an open fd 2
  is never touched): no file the run opens (a lock, a temp file, the agent's work-order file)
  becomes fd 2, and a child that inherits stderr writes to the null device.
- **Writers** (`registry`, `index`, `proposals apply`, `sync --apply-proposals`, `create`,
  `roles add`, `migrate`) take the registry lock (`<registry>.lock`), write atomically, and refuse a file that
  changed since it was read. `code-map add` appends one rule to `<config_dir>/config.toml` (one
  append-mode write, validated first; never a rewrite). `--dry-run` writes nothing. Field writes (`registry`, `propose`,
  proposals from hooks) refuse a value lint would report as an error for that field: a `status`
  outside `[registry] statuses`, a `related_modules` edge without `module` / `relation` /
  `description`, with an unknown relation, or to an unknown module or child. `init` only
  creates files that do not exist yet (and appends missing `.gitignore` lines). `adopt` writes
  one file in the config dir (never the registry or a doc); `init map` / `init confirm` write
  only `<config_dir>/init/` (and the starter files `init` would create); `eject --rebase`
  rewrites only the ejected copy's `.segmently-modules-ejected` — each through a temp file and a rename,
  except `adopt`'s new `config.toml`: its temp file is hard-linked into place (created
  exclusively, never over a file that appeared meanwhile).
- **`--files PATH …`** (`sync`, `discover`, `sync-instructions`): the flag may be repeated and the
  lists add up (`--files a b --files c` is `--files a b c`); a path that does not exist is still mapped (a
  deleted file is a real change) and listed in `missing_files` (`[]` for `--from-diff`, which
  lists real changes only); a directory is refused (exit `2`, nothing mapped, no hook runs) —
  list its files instead, e.g. `git ls-files <dir>`.
- **`--task-file FILE|-`** (`context`, `discover`, `choose`): the task text from FILE, or from
  stdin for `-`, read as bytes and decoded as UTF-8 whatever the locale (a FILE's `\r\n` and lone
  `\r` become `\n`, as a text-mode read gives them; stdin's are kept); a task file that cannot be
  read or is not UTF-8 is exit `2` with `segmently-modules: error: cannot read <path>: <reason>` (`<stdin>`
  for `-`; `<reason>` is the system's reason or `not valid UTF-8`), never an internal error; an
  empty or whitespace-only text is exit `2` (`give the task: …`).
- **Git refs** (`--from-diff A..B` of `sync` / `discover` / `sync-instructions`, `--base REF` of `lint --changed` and
  `ci`): a
  value starting with `-` is refused (exit `2`) — it would be read as a git option. Changed paths
  are relative to the root and limited to it, also when the root is a subdirectory of the git
  repository; a rename counts as a delete plus an add. `--base` is a two-dot diff against the
  working tree, not a merge base: outside a merge-ref checkout (a plain branch checkout behind
  the target branch), pass `--base "$(git merge-base origin/main HEAD)"` so the target branch's
  own later commits are not counted as changes.

## Files the engine creates

- `<registry>.lock` (default `modules/registry.json.lock`): the advisory lock every writer takes
  — in the per-module layout too, where it guards every `<module>/module.json` and the index
  (`index build` takes the same lock). It stays on disk; ignore it in git.
- `<proposals_dir>/` (default `.segmently-modules/proposals/`): the proposals queue — pending
  `<run_id>-<agent>.json` files, a `<run_id>-<agent>.json.lock` next to each, and `done/` with
  every processed file and its per-item results. Ignore the whole directory unless the team wants
  the queue history in git; then ignore only its `*.lock` files.
- `<agent skills dir>/<skill>/.segmently-modules-managed` (`.claude/skills/`, `.agents/skills/`): written
  last by `segmently-modules packs sync` into every skill it manages — JSON `{"schema": "segmently-modules.managed/1",
  "pack", "skill", "version", "source", "files": {path: sha256}}` (indent 2, sorted keys). Commit
  the managed skill directories with their markers; `segmently-modules packs sync --check` in CI fails when
  they are stale.
- `<config_dir>/overrides/skills/<skill>/` (default `.segmently-modules/overrides/skills/`): a skill the
  team owns, written by `segmently-modules eject`, with `.segmently-modules-ejected` = `{"schema": "segmently-modules.ejected/1",
  "skill", "pack", "version", "files": {path: sha256}}` (the upstream snapshot at eject time) —
  commit it; only `segmently-modules eject <skill> --rebase` rewrites it (the pack's current state, after
  the team took the upstream change by hand), never the copy's files.
- `<config_dir>/init/` (default `.segmently-modules/init/`): the work directory of `segmently-modules init map` —
  `state.json` (the phases and the modules), `state.json.lock` (the lock of every state change),
  `preflight.json`, `proposal.json` (edit it at gate 3), `confirmed.json` (frozen by `init
  confirm`), `work/<module>.json` (the work items of `init fanout`), `staging/<module>/`
  (what the writers write: `MODULE.md`, `roles/<role>.md`, `entry.json`), `staging/registry.json`
  and `reconcile.json` (`init reconcile`), `routing-tasks.json` (`init eval-tasks`, or written
  by hand), `verify.json` (`init verify`) and `pr-body.md` (`init finish --open-pr`). Ignore it in
  git.
- `<config_dir>/adopt.proposed.toml`: what `segmently-modules adopt` would add to an existing
  `config.toml` — merge it by hand, then delete it.
- `<config_dir>/overrides/templates/<template>` (default `.segmently-modules/overrides/templates/`): the
  team's copy of a template, written once by `segmently-modules templates override` and never replaced by
  the engine — commit it.
  A template candidate that does not exist (`lstat` says ENOENT, ENOTDIR or ENAMETOOLONG) falls through to the
  next layer. One that exists but cannot be read — a directory, a FIFO, a dangling symlink or a
  symlink loop, a file or a parent directory without permission, a NUL in the name (shown as `\0`) — is exit `2`
  `segmently-modules: error: cannot read <path>: <reason>` (root-relative inside the root), for every verb
  that resolves a template (`templates list` included) and nothing is written; the layers
  below the winner are never examined. A verb that renders the winner reads it as UTF-8: a
  template that is not UTF-8 is `cannot read <path>: not valid UTF-8`, exit `2` as well
  (`templates list` and `templates override` never decode it).

```gitignore
modules/registry.json.lock
.segmently-modules/proposals/
.segmently-modules/init/
.segmently-modules/config.user.toml
```

`segmently-modules init` appends these four lines (for the configured registry, proposals and config
paths; the last two only when the config dir lies inside the root) when they are missing. The
personal config may hold the user's own settings, so it is never committed. On a registry that
already has modules, `init` prints `next: segmently-modules next` (text only; the JSON is unchanged).

| `adopt` | `[--registry PATH] [--layout single\|per-module] [--dry-run]`: `{root, registry, layout, inferred: {paths, roles, fields, dir_whitelist, updated_at_path, statuses, relations, code_map, code_map_suggestion, budgets, skipped}, config_path, config, lint: {counts, findings}, next_steps, dry_run}` — reads an existing registry as it is and infers the team config the engine needs, from the team layers only (a key only `config.user.toml` declares is written too, its evidence says so) (`paths`: `{key: value}` · `roles`: `[{name, order, standard, modules}]` · `fields`: `[{name, type: [expr], kind, scope, entries}]` · `dir_whitelist`: `[dir]` · `updated_at_path`: a dotted path or `null` · `statuses` / `relations`: `[{value, count}]` — the status values and relation types the registry uses that no team layer allows, by count then value, written to `[registry] statuses` / `relations` (a null, non-string or empty value goes to `skipped`) · `code_map`: `{id, pattern, covered, total, alternatives: [{pattern, covered}]}` or `null` · `code_map_suggestion`: `{pattern, covered, total}` — the best prefix when none reaches 50 %, written COMMENTED OUT (never a rule; | `init` | `{root, layout, files: [{path, status}], dry_run}` — root: `--root`, else the git top-level of the current directory, else the current directory; `status`: `created` · `updated` (`.gitignore` got its missing lines, appended in the file's own `\n` / `\r\n` style, through a symlink to its target) · `exists`; creates only missing files, a second run changes nothing; a `--layout` that conflicts with the configured one is exit 2 naming the conversion (`index split` to per-module; `index build` + `registry_layout = "single"` back); plain `init` never creates `<config_dir>/init/` |
| `init map\|confirm\|status\|resume` | start from existing code (one envelope `segmently-modules.init/1` per action; `map` and `confirm` never prompt) · map `[--layout L] [--dry-run] [--restart]`: `{action, root, files: [{path, status}], preflight, proposal, candidates: [name], unassigned, hints, phase, next, dry_run}` — creates the starter files that are missing (as plain `init`), then phase 1 preflight → `<config_dir>/init/preflight.json` and phase 2 map → `proposal.json` (`unassigned` / `hints` are counts), and stops at gate 3; `--dry-run` computes both and writes nothing; refused (exit 2, nothing written) when the registry has modules (use `adopt`; during an init — modules created by hand after gate 3 — `--restart` is refused too: continue with `init resume`, or take them out of the registry and the modules dir first; `--restart` clears `<config_dir>/init/` first · confirm `[--dry-run]`: `{action, confirmed, included: [name], excluded: [name], status, dry_run}` — gate 3: validates the (edited) proposal — every included candidate named by the `create` rule, names unique, `paths` a non-empty list of globs that match files of the file set, no file claimed by two included candidates, at least one included — and freezes it as `confirmed.json`; `status` `confirmed` · `updated` · `unchanged` (only when gate 3 already passed with these bytes: an interrupted `confirm` confirms again); every problem is named at once (exit 2, nothing written); refused once the fan-out has started (`the fan-out has started — to change the module set: segmently-modules init map --restart`) · status: `{action, phase, phases: {phase: status}, next, modules: {module: {status, attempts, error, existing?, problems?}}, counts: {pending, running, done, failed}, pr}` — `phase` = the phase most recently started, `null` without a state; `phases` lists `preflight`, `map`, `gate-map`, `fanout`, `reconcile`, `eval-tasks`, `verify`, `finish`; the text prints a line per phase and per module (`failed  (attempt 2) exit 3: …`) and the counts · resume: `{action, ran: [phase], phase, next, message}` — re-runs every phase before gate 3 that did not finish (an interrupted phase starts over; a partial output never counts); at gate 3 it runs nothing (exit 0); after gate 3 it continues from the recorded phase: the fan-out when it has not run, every `running` or `failed` module back to `pending` (its staging dir cleared; `message` names them), then `reconcile` once every module is done and `verify` once the routing tasks exist (a refused or interrupted `eval-tasks` — its phase `running` — runs again whether or not a tasks file is there; new tasks are always verified) — and stops (exit 0, `next` names the step) at the first step that needs an agent or a person: pending modules or missing routing tasks without `--executor`, gate 7 without `--open-pr`. `--executor CMD` also runs the pending modules (`run`, as `init run`) and writes missing routing tasks (`eval-tasks`); `--non-interactive` never waits for a person: gate 3 passes as the proposal stands (`gate-map`, as `init confirm`), a run that will need a writer (a module not done, routing tasks missing or refused) without `--executor` is exit 2 naming it before anything runs (`… needs --executor "<command>" (nothing ran)`), and it stops before gate 7 unless `--open-pr` (`finish`, as `init finish --open-pr`; after a failed push or `gh`, `pr` retries only what is left). A failed module, eval-tasks or verify stops the run with exit 1 (stderr `segmently-modules: resume: …`); a finished init is exit 0 with `message` `init is finished`. `ran` lists the steps in order. `init map` and `init confirm` never prompt and take no `--non-interactive`. A corrupt or foreign `state.json` / `proposal.json` (a damaged phase entry included) is exit 2 naming the file and `segmently-modules init map --restart`; a state written by an engine with fewer phases reads the later ones as pending; a failed write is exit 2 `cannot write <path>: <reason>`; `--restart` works with `map` only, `--dry-run` not with `status` / `resume` / the phase 4–7 actions; the state's `phase` is `finished` once `init finish` is done; `--layout` only with plain `init` and `map` |
| `init fanout\|next\|done` | phase 4, one work item per confirmed module (`segmently-modules.init/1`) · fanout: `{action, work, items: [module], existing: [module], status, next}` — writes `<config_dir>/init/work/<module>.json` = `{module, parent, paths, files, files_total, neighbours: [{to, imports}], roles, staging_dir, prompt}` per included module of `confirmed.json` (`files`: the first 200 files its paths match, in path order; `neighbours`: its import edges to other included modules; `roles`: the roles `create` scaffolds; `staging_dir`: `<config_dir>/init/staging/<module>`; `prompt`: rendered from the template `init/module_prompt.md`, no `${…}` left) and every module's state `pending`; a module already in the registry gets `existing: true`, `prompt: null` and state `done` — never rewritten; `status` `written` · `unchanged` (a re-run while every item is pending writes the same bytes); refused (exit 2, nothing written) before gate 3, once an item is no longer pending (`init resume` / `init run`), when `<modules_dir>/<module>/` exists without a registry entry, or when a work item file already there cannot be read (`cannot read <path>: <reason> — remove it, then run segmently-modules init fanout; nothing written`) · next: `{action, item, path, counts: {pending, running, done, failed}}` — claims the first pending module by name (`running`, `attempts` + 1, its staging dir cleared, its `error` and `problems` dropped); after a refused attempt of `init run` (`problems` in its state entry) `item` = the work item + `previous_problems: [problem]`, its `prompt` followed by a section `## The previous attempt was refused` listing them (the work item file is unchanged; the same for every claim: `init run`, `init resume --executor`); `item: null` when none is pending; a work item file that is missing is exit 2 before anything is written, its `problems` kept (`<config_dir>/init/work/<module>.json is missing — write the work items again: segmently-modules init fanout` while no module has been claimed yet, else `— start over: segmently-modules init map --restart`); so is one that is damaged: not a JSON object, or a field the engine reads of another shape (`module` not its file's name, `roles` not a list of strings, `prompt` not a string: `<config_dir>/init/work/<module>.json: roles is not a list of strings — fix it, or start over: segmently-modules init map --restart`); the text prints the work item path and the prompt · done `MODULE`: `{action, module, status, problems, message}` — checks the staging output of a running (or failed) module: exactly `MODULE.md`, `roles/<role>.md` per role and `entry.json`, no file empty, a symlink or holding one of the templates' own placeholders (`${<name>}`, or `${<name>` without its brace, for a placeholder name of the resolved `MODULE.md`, the item's role templates or `init/module_prompt.md` — any other `${…}` is text) (a symlinked staging dir is one problem, its target never read), `entry.json` an object with only `description` (`[create]` limits), `keywords` (at least `[create] min_keywords` distinct), `related_modules` (targets: confirmed or registry modules; relations from `[registry] relations`; a description each) and the fields `create` asks for, then the invented-component check of `init verify` over `MODULE.md` and every role doc that could be read (a path exists inside the root, or is a doc `init finish` will write: `<modules_dir>/<module>/<module_doc>` and `roles/<role>.md` of any work item of this init; a component row's symbol occurs in its file) — one problem per finding, in doc and line order after the file problems and before the `entry.json` ones: `<doc>:<line>: path does not exist: <path> (write paths from the repository root, as in the file list)` · `<doc>:<line>: symbol not found in its row's file: <symbol>` · `<doc>:<line>: no file to check: <symbol>` · `<doc>:<line>: line past the end of its doc: <doc>:<n>` (a rules-index citation) → `done` (exit 0); else exit 1, `status` unchanged, one stderr line `segmently-modules: <module>: <problem>` per problem; a done module: exit 0, `message` `already done`; the check runs outside the lock, so a module put back or claimed again meanwhile is not marked (exit 1, `changed while it was checked …`); a pending module (`claim it first: segmently-modules init next`) or an unknown one: exit 2; so is a template the placeholder rule cannot read (`cannot read <path>: <reason>`) and the module's own work item missing (named with the way out, as for `next`) or damaged (not a JSON object, or of the wrong shape, as for `next`). Every state change is a read-modify-write under `<config_dir>/init/state.json.lock` (a writer that waits past 10 s is exit 2 naming it) |
| `init run --executor CMD` | phase 4 for CI, every pending module through one command, `[init] max_parallel` at a time: `{action, modules: [{module, status, attempts, error}], counts, outside: [path], failed, next}` — first puts every `running` / `failed` module back to `pending` (its staging dir cleared); CMD is split with `shlex`, never run by a shell (`>`, `\|`, `$HOME` are plain arguments); its first word is found on `PATH`, or — holding a `/` — resolved against the root; empty, unbalanced quotes, not found or not executable is exit 2 before any module runs (`--executor is empty` · `--executor: No closing quotation` · `executor not found: …` · `executor is not executable: …`). Per module: stdin = its prompt (UTF-8, then EOF), cwd = the root, the caller's environment plus `SEGMENTLY_MODULES_INIT_MODULE` (the name), `SEGMENTLY_MODULES_INIT_STAGING`, `SEGMENTLY_MODULES_INIT_WORK` (absolute paths of its staging dir and work item); stdout is discarded. Exit 0 and a complete staging output (`init done`'s check) → `done`; exit 0 and a refused output → back to `pending` with `problems` (the list) and `error` (`; `-joined) in its state entry and retried once in this run through a normal claim (its prompt ends with the problems; a stderr line `segmently-modules: <module>: refused — retrying once`; one retry per module per run, a new `init run` or `init resume --executor` grants another; a claim another driver won first leaves it to that driver) — refused again → `failed` with `error` and `problems`; a retry whose claim is refused (its staging dir left a symlink or not removable, its work item missing or damaged) → `failed`, `error` = the problems + `; the retry could not start: <reason>`, `problems` kept, the other modules run on; a check that cannot run (a template it cannot read, the module's own work item missing or damaged) → `failed` at once, `error` = `the check could not run: <reason>`, no retry; any other exit → `failed` at once, no retry, `error` = `exit <n>: <the last 20 stderr lines, at most 2,000 characters>` — a stderr line `segmently-modules: <module> failed: …` each. `modules` has one row per module, its last attempt. A module another driver claimed first (`init next`, a second `init run`) is left to it: its executor never starts; one another driver put back or claimed again while its executor ran (`init resume`, `init next`) is left to it too — nothing written, no row, no retry. In a git work tree the changed and untracked files outside `<config_dir>/init/` are compared before and after (`git status -z`, content hashed in chunks; a symlink by its target text, never followed; the source of a rename or copy into the work dir counts as outside): each new or changed path is `outside` and a stderr line `segmently-modules: wrote outside the staging dir: <path>`. Exit 1 when a module failed or a path is `outside`; nothing pending: exit 0, `modules: []`. No timeout: stop a hung run with Ctrl-C (exit 130; its executors are terminated — 5 s for all of them, then SIGKILL — and their modules stay `running`) and continue with `init resume`. `--non-interactive` is accepted and changes nothing (it never prompts) |
| `init reconcile` | phase 5, a script (no agent, no command but git): `{action, staging_registry, reconcile, edges, collisions, duplicates, judgement, next}` — needs every module `done` (else exit 2 naming each module that is not, with its status; nothing written); writes `<config_dir>/init/staging/registry.json` = the registry's own modules as they are, then one entry per new module in name order: `{name, description, status: "active", keywords, context_files: {universal, roles: {role: path}}` (the final paths of `create`'s layout)`, <the fields create asks for>, related_modules?}` (the house serializer), and `<config_dir>/init/reconcile.json` = `{edges, collisions, duplicates, judgement}`: `edges` `[{from, to, relation, source: "imports" \| "writer"}]` — the proposal's import edges between confirmed modules added as `{module, relation: "depends-on", description: "imports from <to> (<n> import(s), init reconcile)"}`, one per direction, a writer's own edge to the same module (any relation) kept instead; `collisions` `[{keyword, owner, others, files: {module: n}, removed}]` — a keyword (any case) that two new modules or more hold: the owner is the module with the most files under its confirmed paths whose path or text holds it as a whole word (the `match` rule; a file counts once), another holder loses it from `keywords` only when none of its own files holds it (`removed`; a holder whose files hold it keeps it — the text line says `kept by <module>, … (their files hold it)`; never a negative keyword) — unless that leaves one below `[create] min_keywords` (judgement `{kind: "keyword-floor", keyword, module, keywords}`), and on a tie nothing is removed (`owner: null`, judgement `{kind: "keyword-tie", keyword, modules, files}`); `duplicates` `[{name, definitions: [{module, file, line}]}]` — a name defined in two confirmed modules or more, at least one of them new (a module already in the registry counts as the other; a name only modules already in the registry share is not reported) (Python top-level `def` / `class`; JS/TS `export function\|class\|const\|interface\|type`), never one starting with `_`, a re-export, `export default` or a test file (`test_*.py`, `*_test.py`, `*.test.*`, `*.spec.*`, under `tests/`), each also a judgement `{kind: "duplicate", name, definitions}`; `judgement` sorted by kind, then keyword or name; every list sorted. ## Semantic module choice (`--match`)

`match`, `context` and `discover --task` find modules by keyword (`lexical`, the default; their
output is byte-identical to earlier versions). `[match] mode` or `--match MODE` (the flag wins)
switches them:

- `lexical` — the rows come from the keyword routing alone, nothing else runs;
- `semantic` — from the user's own agent alone (the picks of `segmently-modules choose`; a row has its `confidence` and no `score`);
- `hybrid` — from both, fused by reciprocal rank fusion (k = 60): a row's score is the sum of `1/(60 + rank)` over the lists that hold it, ties by keyword rank, then module name.

The engine holds no model, no API key and no network code, and ships and suggests no model: the
agent is a command the user configured in `SEGMENTLY_MODULES_AGENT_COMMAND` ([configuration.md](configuration.md#the-agent-command-and-search)),
asked ONCE per run with the work order of `segmently-modules choose` (no cache; on its stdin as compact JSON).
A `--top` of `0` asks nothing (`match` and `context` in `semantic` mode then print
`no module matched (--top 0)`); a registry without modules asks nothing either and says so in the
note `the registry has no modules: the agent was not asked`. `match` and `context` in `semantic`
mode without a row print `no matches (the agent chose no module; try rephrasing the task)` and
`no module matched (the agent chose no module; try rephrasing the task)`.

- **JSON, `semantic` / `hybrid`:** `match` prints `{mode, rows, notes}` (not the plain list);
  `context` and `discover` keep their document and gain `mode` and `notes`. In `match` and `context`
  a row carries `sources` (`["keyword"]`, `["semantic"]` or both); a row the agent listed also has
  its `confidence` (0..1) and `reason` when the agent gave one; a hybrid row also has `rrf` (the
  fused score, 6 decimals). A row only the agent found has no `score`, `keywords` or `negative`.
  In `discover` a row keeps its `score` (`null` for a row only the agent found), its `sources` list
  gains `semantic` next to `keyword` / `diff` / `path`, and it gains `confidence` when the agent
  listed it — no `reason` and no `rrf`. A lexical run
  has none of `mode`, `notes`, `confidence`, `reason`, `rrf`.
- **A mode from a config file needs the user's opt-in:** with a non-lexical `[match] mode` and no
  `--match`, the run is lexical unless `SEGMENTLY_MODULES_AGENT_ALLOW_REPO_MODE=1` (`0`, empty and unset are
  off; any other value is exit `2`, nothing on stdout, stderr
  `segmently-modules: error: SEGMENTLY_MODULES_AGENT_ALLOW_REPO_MODE: expected 1 or 0, got '<value>'`, at most 40 characters of the value). Off: stdout (text and JSON) is byte-identical to `--match lexical`
  and stderr carries exactly one line, printed after stdout and only when the run exits `0`:
  `segmently-modules: note: [match] mode "<mode>" is set in a config file; it runs your agent command only with SEGMENTLY_MODULES_AGENT_ALLOW_REPO_MODE=1 (or pass --match <mode>) — ran lexical`.
  `segmently-modules: note:` is a stderr-only prefix; a refused run keeps its single `segmently-modules: error:` line.
  The `segmently-modules: note:` lines (stderr only, after stdout, only when the run exits `0`): the one above
  and `catalog`'s `segmently-modules: note: <variable>: <problem> — match.semantic is false` (a malformed
  `SEGMENTLY_MODULES_AGENT_COMMAND` or `SEGMENTLY_MODULES_AGENT_TIMEOUT`).
  `--match`, `choose --run` and `catalog` need no opt-in and never read it.
- **`semantic` without an agent command:** exit `2`, nothing on stdout, stderr
  `segmently-modules: error: semantic matching needs your agent: set SEGMENTLY_MODULES_AGENT_COMMAND (a JSON array); in Claude Code / Codex the skills do it with segmently-modules choose`.
- **`hybrid` without one:** exit `0`, the lexical rows, and the note `semantic part skipped: no agent command configured` (text: a line after the rows; JSON: `notes`).
- **Inside an agent run** (`SEGMENTLY_MODULES_WORK_ORDER` is set for the agent's own process): `semantic` is exit `2`
  (`already inside an agent run (SEGMENTLY_MODULES_WORK_ORDER is set): a nested agent call is refused; use lexical matching or segmently-modules choose --task`);
  `hybrid` runs lexically with the note `semantic part skipped: nested agent call`.
- **An agent that fails** (a non-zero exit, a timeout of `SEGMENTLY_MODULES_AGENT_TIMEOUT` seconds, more than
  4 MiB on stdout, no answer in the output, an answer that breaks the schema) is exit `2` with
  `segmently-modules: error: agent …`; Ctrl-C, SIGTERM or SIGHUP during the call is exit `130` — a repeated
  one too: the agent's process group is killed and the temp files removed. Never a traceback.
- **`segmently-modules catalog`** prints the cards an agent reads (`match.mode`, `match.semantic`, `search`), with every keyword — the work order caps them at `[search] card_keywords`;
  **`segmently-modules choose --task TEXT`** prints the work order (`segmently-modules.choose/1`); the agent answers
  `{"picks": [{"module", "confidence", "reason"}], "none": bool, "catalog_digest": "<the order's digest>" | null}`; **`segmently-modules choose --apply FILE|-`**
  validates that answer offline (unknown module ids are dropped with a note each, a different
  `catalog_digest` is a note, more than `max_picks` keeps the top ones with a note; exit 2 for JSON
  or schema that does not fit) and prints each pick with its `read` docs; **`segmently-modules choose --task TEXT --run`**
  does both through the agent command. The answer's schema is the strict-mode kind (every
  property required, no extra keys), so `claude -p --json-schema` and `codex exec --output-schema`
  accept it as it is; `--apply` itself is lenient (`none`, `reason` and `catalog_digest` may be missing, extra keys are ignored). The agent's stdout — and the input of `--apply` — may be the answer itself or a `claude -p --output-format json`
  envelope (its `structured_output`, else `result`; a string `result` may be wrapped in one json code fence).

## Pipeline stages

| Stage | Command |
|---|---|
| before plan | `segmently-modules context --task "…" --role developer --json` |
| after plan | `segmently-modules discover --task-file plan.md --json` |
| CI, no task text | `segmently-modules discover --from-diff $BASE..HEAD --json` |
| during build | `segmently-modules propose --run-id $RUN --agent builder --module M --op … --reason "…"` |
| after build | `segmently-modules sync --from-diff $BASE..HEAD --apply-proposals --run-id $RUN --json` |
| by meaning | `segmently-modules choose --task "…" --json` → the user's agent answers → `segmently-modules choose --apply - --json` (or `--run`) |
| docs follow-up | `segmently-modules sync-instructions --from-diff $BASE..HEAD --json` — per touched module: the docs to update, the drift, the field hints |
| adopting a registry | `segmently-modules adopt --dry-run --json` — the inferred config and the lint it would leave; then `segmently-modules adopt` |
| starting from code | `segmently-modules init map --json`, edit `<config_dir>/init/proposal.json`, `segmently-modules init confirm --json` |
| CI gate | `segmently-modules ci --base $BASE --fail-under 80 --json` — lint (plain: config-level findings MS021, MS052, MS053 and the pack checks MS06x appear only here), drift against `$BASE` (a real ref: the PR's target branch or a captured pre-change commit) and coverage, always all three |
